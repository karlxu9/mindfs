> 生成日期：2026-08-22　|　基线：第一轮（`docs/fork-plan.md`）已全部收尾（阶段 0 ～ 阶段 3）　|　当前上游版本 v0.4.9
>
> 配套文档：[软件设计文档](./round2-design.md) · [开发计划](./round2-devplan.md)

## 1. 背景与目标

### 1.1 背景

第一轮二开解决的是"每天都在用、每天都在疼"的显性痛点（项目复活、批量删除、补全手感等）。第二轮启动前做了三项专项代码调查（数据存储与备份、服务生命周期、通知/定时/日志），交叉印证出一个共同结论：

**MindFS 作为一个 7×24 长跑、承载个人数据资产、主要靠手机远程访问的服务，其"停止/重启/更新"路径、数据备份能力和远程自诊断能力，三者都处于事实缺失状态。**

调查确认的核心事实（详细论据见设计文档 §1）：

1. **优雅退出名存实亡**。`server/app/server.go:192-197` 的清理协程会输给进程退出的竞态（`cli/cmd/mindfs.go:367` 信号一到 main 立即返回）；Windows 上 `-stop`/`-restart` 是 `taskkill /T /F` 强杀；Web 触发的自更新直接 `os.Exit(0)`。约 10 类长生命周期资源在退出时无人关闭。
2. **强杀有真实损害**。`fs/registry.go:141` 用非原子的裸 `os.WriteFile`，强杀撞上写入窗口会**丢失全部托管目录配置**；claude CLI 子进程和 commandexec 长驻 shell 会残留为孤儿进程（Windows 尤甚）；kanban 执行中的任务停在 `running` 脏状态。
3. **会话历史零备份能力**。数据分散在三处（项目内 `.mindfs/`、`~/.mindfs/<rootId>/`、用户配置目录下的兜底 sqlite + `.link` 指针），没有任何导出/备份/恢复功能；`.mindfs/` 被 `.gitignore` 忽略，不随 git 备份。
4. **远程无法自诊断**。`/health` 只返回字面量 `"ok"`；无任何日志查看 API；前端无诊断面板。日志只在守护进程启动那一刻轮转一次（`cli/cmd/mindfs.go:523`），长跑必然无限增长。
5. **前端崩溃即白屏**。`web/src/components/ErrorBoundary.tsx` 实现完整（含 i18n、重试按钮、两个特化变体）但**全仓零引用**，是死代码。
6. **若干一行级缺陷**：`agents-env.json` 以 0644 权限存 API Key 明文（`api/agent_config.go:728`）；删除会话遗漏 `.debug.jsonl` 清理（`session/manager.go:1069-1086`）；Agent 会话出错只推 WS 不发推送（`appcontext.go:882`）；`fatal` 级 toast 被静默丢弃（`Toast.tsx:18`）；定时任务无执行超时、卡死一次即永久停摆（`scheduled/tasks.go:326`）。

### 1.2 目标

本轮不新增大功能，聚焦三件事：

| 目标 | 衡量方式 |
|---|---|
| **停得下来**：任何停止/重启/更新路径都完成资源释放，不留孤儿进程、不损坏配置 | 验收标准 R-1 全通过 |
| **备得走**：会话历史与配置可一键打包导出、按文档恢复 | 验收标准 R-5 全通过 |
| **看得见**：远程（手机）可查看服务日志与健康状态；前端不再白屏 | 验收标准 R-2 / R-4 全通过 |

### 1.3 非目标（明确不做）

| 项 | 不做的理由 |
|---|---|
| SQLite migration 版本号框架 | 上游用"幂等 ALTER + 错误字符串匹配"持续演进 schema。引入框架 = 每次上游加字段都要手工翻译成 migration，是**永久性合并冲突税**。个人场景下现状虽土但能用。 |
| 会话回收站 / 软删除 | 需改 `sessions` 表 schema（上游高频区），批量删除已有含子会话数量的二次确认，收益不抵冲突成本。 |
| `.aux.jsonl` 写入端瘦身/压缩 | 写入逻辑在上游高频演进区（stream/toolcall 处理）。本轮只做**体积可见性**（R-5.3 存储体检），瘦身留待上游动作或下轮评估。 |
| Windows 凭据文件 ACL 完整加固 | `os.Chmod` 在 Windows 只切只读属性的问题（fork-plan §阶段 0.5 已记录）需设 ACL，成本中等而个人单机风险低。保留为观察项，本轮仅做 R-3.1 的 Unix 侧权限统一。 |
| `App.tsx` 专项拆分 / 任务看板优化 | 延续第一轮决策：前者随手拆，后者等痛点清单。本轮前端新增均为独立组件 + 最小接线。 |

## 2. 用户与场景

**用户画像**：单人使用者，Windows 11 主力机常驻运行 MindFS（开机自启），白天在电脑前、通勤和外出时用手机（PWA + Relay）远程驱动 Agent。会话历史是数月积累的工作资产。

**关键场景**：

- **S1 关机/重启电脑**：Windows 关机对后台进程无情。用户期望重启后托管目录配置完好、没有残留的 node/claude 进程、看板任务状态不脏。
- **S2 升级 MindFS**：在 Web UI 点更新，期望旧进程干净退出、新进程接手，会话数据无损。
- **S3 换机/重装/防灾**：用户想把全部会话历史和配置带走或存档。当前只能手工 copy 且极易漏掉 home 模式目录和兜底 DB。
- **S4 手机上发现不对劲**：Agent 没响应/任务没跑。当前只能等回到电脑前翻 `mindfs.log`。期望手机上能看到服务日志尾部和各组件健康状态。
- **S5 前端偶发崩溃**：某个渲染 bug 导致白屏，用户只能强刷。期望看到降级 UI 并可局部重试。

## 3. 功能需求列表

优先级定义：P0 = 本轮必须完成；P1 = 本轮应完成，时间不足可顺延到下轮首位；P2 = 顺手做，可整体砍掉不影响本轮验收。

### R-1 优雅退出与进程治理【P0】

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-1.1 | **退出编排**：收到停止指令（Unix 信号 / Windows 停止通道 / 自更新重启）后，服务按序释放全部长生命周期资源，整体上限 10 秒，超时兜底强退并记日志 | ① Unix 上 `kill -TERM` 后进程在 10s 内退出，日志出现完整的关闭序列记录；② 退出后系统中无 mindfs 派生的残留进程（claude CLI、ACP agent、长驻 shell 及其子进程）；③ `.mindfs/` 下无 `*-journal` 残留文件；④ kanban 中无停留在 `running` 的 stage run（执行中的被标记为中断态或已收敛）；⑤ 反复 `-restart` 20 次后 `registry.json`、`preferences.json` 内容完整可解析 |
| R-1.2 | **Windows 优雅停止通道**：`-stop` / `-restart` 优先通过本地鉴权的关机 API 请求服务自行退出；等待超时（5s）或 API 不可用时回退现有 `taskkill` 路径 | ① Windows 上 `mindfs -stop` 默认走 API 路径且达成 R-1.1 的全部退出效果；② 服务无响应（模拟挂死）时 `-stop` 在超时后仍能通过 taskkill 完成停止；③ 关机 API 仅接受携带本地 CLI token 的 loopback 请求，无 token 或远程来源返回 401/403 |
| R-1.3 | **自更新走退出链**：Web 触发的自更新重启不再 `os.Exit(0)`，改为触发 R-1.1 的退出编排后再退出，替换脚本时序不变 | ① Windows/Unix 上从 Web UI 触发更新，旧进程达成 R-1.1 效果后退出，新版本正常起服务；② 更新全程会话数据与 `registry.json` 无损 |
| R-1.4 | **关键 JSON 原子落盘**：`registry.json` 及同类裸 `os.WriteFile` 落盘点（relay 凭据 ×2、relay 服务映射、prompts、agent 配置 ×4，共 9 处，清单见设计文档 §3）统一改为临时文件 + rename | ① 9 处全部走统一原子写路径；② 现有相关测试全绿；③ 写入中途注入失败（测试模拟）不产生半截文件，原文件保持旧内容完整 |

### R-2 前端崩溃与错误可见性【P0】

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-2.1 | **接线 ErrorBoundary**：主视图与抽屉面板分别包上现成的 `MainViewErrorBoundary` / `DrawerPanelErrorBoundary` | ① 在主视图内人为抛出渲染错误（测试挂钩），显示降级 UI 而非白屏，点"重试"可恢复；② 抽屉内崩溃不影响主视图；③ 崩溃信息进入 console 供排查 |
| R-2.2 | **fatal 错误兜底**：`severity: "fatal"` 的错误不再被 Toast 静默丢弃，以不自动消失的持久提示呈现 | report 一个 fatal 错误后界面出现持久提示，需手动关闭；非 fatal 行为不变 |
| R-2.3 | **会话出错推送**：Agent 会话进入错误态时（现 `BroadcastSessionError` 路径）发出 `session.error` 通知，Web Push 与 notify-script 两通道同 payload | ① 会话出错时手机 PWA 收到推送，点击跳转到该会话；② notify-script 收到 `type: "session.error"` 的 payload；③ 与 `session.done` 一样有 30 分钟去重 |

### R-3 数据安全小修包【P0】

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-3.1 | `agents-env.json`（含 API Key 明文）落盘权限从 0644 收紧为 0600，与 `credentials.json` 一致 | Unix 上新写入的文件权限为 0600；Windows 上行为不回退（沿用现有平台跳过约定） |

### R-4 远程可观测【P1】

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-4.1 | **运行期日志轮转**：日志大小检查从"仅启动时"改为写入路径持续生效，沿用现有 10MB × 3 备份策略；日志文件名按监听地址区分（与 PID 文件一致化），修复多实例交叉写入；macOS launchd 自启动场景轮转同样生效 | ① 长跑进程日志写满阈值后自动滚动，产生 `.1/.2/.3` 备份且主文件重新计数；② 两个不同端口的实例各写各的日志文件；③ macOS 自启动实例的日志同样受轮转约束 |
| R-4.2 | **日志查看 API + 前端入口**：提供拉取日志尾部 N 行的 API（默认 200 行，上限 2000），前端在侧边栏菜单新增"诊断"入口展示，可刷新 | ① 手机远程访问时能看到最近日志并刷新；② API 需通过既有会话鉴权（与其他 `/api/*` 一致），Relay 模式下同样可用；③ 日志内容按等宽正常渲染，不因单行超长破版 |
| R-4.3 | **诊断状态端点**：新增聚合状态 API：版本、启动时间/uptime、各托管 root（含 meta 位置与会话数）、agent 探测结果摘要、webpush 订阅数、relay 连接状态、定时任务概况 | ① 前端诊断页展示上述信息；② 字段清单与设计文档 §5 一致；③ 端点响应时间 < 500ms（不做重扫描，读内存态） |

### R-5 数据备份与导出【P1】

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-5.1 | **一键导出备份包**：按单项目或全部项目导出 zip，内容覆盖三处分散存储（项目 `.mindfs/`、home 模式目录、`.link` 指向的兜底 sqlite），sqlite 以一致性快照方式导出，包内含 `manifest.json`（版本、时间、rootId→原路径映射、meta 位置模式）与 `RESTORE.md` 恢复说明 | ① 对 project 模式、home 模式、`.link` 兜底三种布局各造一个项目，导出包均包含其全部会话数据；② 导出期间有会话正在写入，包内 sqlite 可正常打开且无损坏；③ 包内 `manifest.json` 字段与设计文档 §4 一致 |
| R-5.2 | **备份包可恢复**：按 `RESTORE.md` 步骤把备份包恢复到一台干净环境（或清空后的本机），启动 MindFS 后历史会话完整可见、可继续对话 | 三种布局各恢复一次，会话列表、会话正文、看板任务、定时任务定义全部可见；此条是 R-5 的发布硬门槛 |
| R-5.3 | **存储体检与清理**：按 root 展示存储占用报表（会话数、正文/aux/debug jsonl 体积、db 体积），检测垃圾文件并清理——孤儿 `.debug.jsonl` 直接删除；`*-journal` 残留采用安全回收（触发 sqlite 自行回滚消除，绝不直接删文件，详见设计文档 §4.4） | ① 报表数字与磁盘实际一致（抽样核对）；② 人为制造孤儿 debug 文件与 journal 残留后，体检能列出、清理/回收后消失；③ 清理不误删活跃会话的任何文件，不损坏任何 db |
| R-5.4 | **前端入口**：导出与体检入口放在侧边栏菜单（与"诊断"同区），导出前提示"备份包包含 API Key 等明文凭据，请妥善保管"，并提供"不含用户级凭据"的导出选项 | 勾选排除选项后，包内不含 `credentials.json`、`agents-env.json`、`autostart-environment.json` 等凭据类文件（完整清单见设计文档 §4） |

### R-6 定时任务可靠性【R-6.1/6.2 为 P1，其余 P2】

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R-6.1 | **执行超时**：单次执行加超时（默认 60 分钟，任务级可配），超时后中止本次执行、释放并发锁、记录超时错误；任务不再因一次卡死而永久停摆 | 模拟一次永不返回的执行，超时后 `running` 锁释放，下一个 cron 周期正常触发 |
| R-6.2 | **错误不被覆盖**："previous run still active" 不再写入 `LastError` 覆盖上一次真实失败原因，改为独立的跳过计数/时间字段 | 一次真实失败后紧接一次并发跳过，UI 上仍能看到真实失败原因 |
| R-6.3 | **执行历史**：每任务保留最近 20 次执行记录（开始/结束时间、结果、错误摘要），在任务对话框内可查看 | 连续触发多次后历史按时间倒序展示，超过 20 条自动淘汰最旧 |
| R-6.4 | **cron 友好性**：支持 `@daily` / `@every` 等 descriptor；`NextRunAt` 与 `LastRunAt` 时区口径统一（均转为 UTC 存储、前端本地化展示） | ① 输入 `@daily` 可保存并按预期触发；② 前端展示的上次/下次运行时间对同一任务时区一致 |

## 4. 非功能需求

| 编号 | 需求 |
|---|---|
| N-1 | **上游友好**：新逻辑尽量落在新文件/新包（沿用 `projectscan` 先例）；对 `server/app/server.go`、`cli/cmd/mindfs.go`、`App.tsx` 等上游高频文件的改动收敛为"最小接线"。 |
| N-2 | **平台矩阵**：所有涉及进程/文件系统行为的需求必须在 Windows 与 Unix（CI 的 ubuntu runner）双平台验证；沿用第一轮 CI 双矩阵。 |
| N-3 | **安全边界**：关机 API 仅限 loopback + 本地 CLI token；日志/诊断 API 走既有会话鉴权；备份包含凭据时必须有明示提醒与排除选项。 |
| N-4 | **性能**：诊断端点读内存态不做重扫描；存储体检做磁盘遍历，允许秒级耗时但需异步化，不阻塞其他请求；日志轮转写路径的额外开销不可感知。 |
| N-5 | **可回滚**：每个需求独立成 PR 粒度提交，任一条目可单独 revert 而不牵连其他。 |

## 5. 发布判定

- P0（R-1 ～ R-3）全部验收通过，且 CI 双平台全绿，方可合入 main 并打 fork 版本。
- R-5.2（备份可恢复）是 R-5 的硬门槛：**恢复验证不通过，导出功能不得发布**——只出不进的备份是假安全感。
- P2 条目不影响发布判定。
